# Ink Desk — Security and Stability Report

The learner's rule (`scope.md > Revision — Ink Desk Studio v3`, item 9): an audit **before and after the build**, written here with severity and fix status. This is the **before** audit, 2026-10-14, of `main` at the v2 freeze (`e70d4df`), read as if the app were deployed publicly today.

**How it was done.** Two read-only audit agents (security; crash and robustness) read every route under `app/api/**`, the store, the queue and the providers' clients, and reproduced what they could with throwaway scripts outside the repo (no paid calls, no repo edits). An **adversarial verifier** per audit then tried to refute every finding against the code and Next 16.4's own docs; a finding stays only if it survived. **All 33 survived.** A history scan of all 80 commits for key-shaped strings found none, and `.env` was never committed.

**Status legend:** `open` — not fixed; `fixed in <commit>` — fixed and verified; `accepted` — the learner chose to live with it, with the reason. The *Closed by* column names the v3 slice (`checklist.md`) whose verification must prove the fix. The **after** audit (slice 23) re-runs both lenses on the frozen build and updates every row.

### SEC-01 — No authentication or authorization on any route or page: every project can be listed, read, edited and spent from (IDOR on project ids)

- **Where:** `app/api/projects/[id]/route.ts`:13 · **Severity:** critical · **Closed by:** slice 19 · **Status:** open
- **Scenario:** No proxy.ts or middleware exists, and no handler checks who is calling. The ids are random UUIDs, but they don't need to be guessed because the listing hands them all out.

### SEC-02 — Anonymous, unmetered spending of the owner's OpenRouter/Anthropic credit, with no rate limit, quota or global budget cap

- **Where:** `app/api/projects/[id]/synopsis/route.ts`:35 · **Severity:** critical · **Closed by:** slice 20 · **Status:** open

ANTHROPIC_API_KEY is not set in this environment, so every text call goes to the OpenRouter fallback `openai/gpt-5.6-terra`. A schema-refused or 5xx reply is retried once, so the worst case is about $7. 100 such requests in parallel spend about $350 within a minute or two; via Claude it would be …

### SEC-03 — Unbounded string and array lengths, plus no request-body limit: cost amplification, OOM crash, and projects bricked past Mongo's 16 MB …

- **Where:** `lib/schemas.ts`:237 · **Severity:** high · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** Fields with no `.max()`: SynopsisRequestSchema `pitch/genre/tone`; ChapterPatchSchema `pitch.*`, `synopsis.title/body` and `cast.*.name/role/look/traits[]`; NewProjectSchema `story.*`; RerollRequestSchema/SheetRequestSchema/ImportRequestSchema `id`. Route handlers have no body-size limit (the Next 16 route docs say so, and the upload route's own comment notes it). `proxyClientMaxBodySize` only buffers up to a limit and logs a warning, and only when a proxy exists. Consequences: (a) Cost amplification. Patch `synopsis {title, body: 3.5 MB, accepted:true}`, then call `/cast` once, then repeat `/cast/reroll` or `/sheet` with reuseDna:false. Each call sends the whole synopsis body to the model, about $1.75 to $3.55 per call (scenario mode clips at 12k characters; pitch mode does not). (b) Crash. One `POST` with a several-GB JSON body makes `req.json()` buffer it all, the Node process runs …
- **Fix:** Give every request string a `.max()`: pitch 4,000, genre/tone 60, synopsis title 200 and body 4,000, name 80, role 120, look 1,500, traits max 6 items of max 60 each, ids `.regex(/^[a-z0-9-]{1,64}$/)` or `.uuid()`. Use `.strict()` on request objects. Add a shared `readJson(req, maxBytes)` helper that rejects a missing or oversized Content-Length and then streams `req.body` with a running byte counter, aborting with 413 when the cap is passed (64 KB for JSON, 100 KB for the scenario patch). Use the same streaming cap for the multipart upload (SEC-05). Optionally refuse a project document over about 1 MB in `updateProject` before writing.
- **Verifier:** Reproduced with tsx: SynopsisRequestSchema, ChapterPatchSchema (synopsis.body and cast look/traits), NewProjectSchema.story and SheetRequestSchema.id all accept 3.5 MB strings, and traits accepts 10,000 items. The Next 16.4 docs set no body limit for route handlers. bodySizeLimit applies only to Server Actions, and proxyClientMaxBodySize only to proxy, which does not exist. The cost amplification works: assertStoryEditable allows a synopsis patch until the cast exists, and storyBrief returns …

### SEC-04 — Upload size cap is bypassable (it trusts Content-Length; chunked bodies are fully buffered by formData()), and there is no storage quota

- **Where:** `app/api/projects/[id]/assets/route.ts`:20 · **Severity:** high · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** The 3.75 MB guard reads the declared `content-length` header, and `Number(null ?? 0)` passes a chunked request that has no Content-Length. `req.formData()` then buffers the whole multipart body in memory before `file.size` is checked, so a multi-GB chunked upload crashes the process. Separately, each project holds 24 assets × 3.75 MB (about 90 MB), and anyone can create unlimited projects (`POST /api/projects` has no limit). A loop of create project plus 24 uploads fills the server disk in local mode, crashing writes for every user, or grows the R2 bill without limit in cloud mode.
- **Fix:** Require Content-Length on multipart (411 if missing), reject anything over the cap, and also count the bytes actually streamed (wrap `req.body` in a TransformStream that errors past UPLOAD_LIMIT + 64 KB) before calling formData, or parse multipart with a streaming parser such as busboy with `limits.fileSize` and `limits.files=1`. Add per-user storage quotas (for example 200 MB per user and 24 assets per project) and a per-user cap on project count. Add a delete for assets and projects that also deletes the blobs.
- **Verifier:** Confirmed at app/api/projects/[id]/assets/route.ts:20. A chunked request has no content-length, so Number(null ?? 0) is 0 and passes the guard. req.formData() then buffers the whole body before the file.size check runs. The only prerequisite is a valid project id, which SEC-01 hands out. checkUpload caps each project at 24 assets, but project creation is unlimited and there is no delete, so disk or bucket use can grow without bound. High is right for a public deployment.

### SEC-05 — Upload validation is magic bytes only: arbitrary payloads are stored and re-served from the app's origin, EXIF/GPS is kept, and nosniff is …

- **Where:** `lib/assets.ts`:46 · **Severity:** medium · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** `sniffImage` checks only the first 3 bytes for JPEG (FF D8 FF), 8 for PNG, and the RIFF/WEBP header. A file of `FF D8 FF` followed by a ZIP, an EXE, or HTML/JS is accepted, stored, and served by `GET /api/image/asset-<uuid>.jpg` to anyone, with a year-long immutable cache and no `X-Content-Type-Options: nosniff`. The type is image/jpeg and the ids allow no SVG, so script execution is unlikely in modern browsers. The real risks are free malware/payload hosting on the app's domain (which can get the domain flagged by Safe Browsing) and content-type confusion in older clients. Uploaded photos are not re-encoded either, so EXIF metadata, including GPS coordinates of a user's real photo, is stored. Once public sharing ships it is served to the world, and it is sent to Claude/OpenRouter today.
- **Fix:** Decode and re-encode every upload server-side, for example with `sharp`: verify it decodes, enforce maximum pixel dimensions (say 4096×4096, which also guards against decompression bombs), `.rotate()` to apply orientation, then output PNG/WebP with all metadata stripped. Store only the re-encoded bytes. On `/api/image/[id]` add `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and `Cross-Origin-Resource-Policy: same-site`. Add `Content-Disposition: inline; filename=...` with a sanitized name.
- **Verifier:** Reproduced: checkUpload accepts FF D8 FF followed by HTML/script and labels it image/jpeg. saveAsset stores the raw bytes with no re-encoding, so EXIF/GPS is kept. The image route sets no nosniff. Script execution is unlikely because the response is served as image/jpeg with a .jpg id, so the practical risks are payload hosting on the app's domain and EXIF/GPS leaks. Medium is justified only because public sharing is in scope; today it is closer to low.

### SEC-06 — Image route serves any matching key with no ownership check; in cloud mode it reads any root-level png/jpg/webp in the bucket

- **Where:** `app/api/image/[id]/route.ts`:15 · **Severity:** medium · **Closed by:** slice 19 · **Status:** open
- **Scenario:** `/api/image/<id>` checks only the id's shape (`^[a-z0-9]+(?:-[a-z0-9]+)*\.(png|jpg|webp)$`), never which project or user the image belongs to. All ids leak through the anonymous project listing (SEC-01), so every sheet, panel, cover and uploaded reference is readable by anyone. In cloud mode, `getBlob` does `GetObject` on that key in the configured bucket. The environment's bucket names (S3_BUCKET_PROJECT_FILES, S3_BUCKET_COMPILE_OUTPUTS) suggest buckets shared with another product. If either is used and holds other root-level objects named like `logo.png` or `report-2026.png`, Ink Desk becomes an unauthenticated read proxy for them. Response headers are also `private, immutable` with no nosniff (see SEC-05).
- **Fix:** Write blobs under a namespaced key: `inkdesk/u/<ownerId>/p/<projectId>/<kind>-<uuid>.<ext>`. Serve them via `/api/projects/<id>/images/<imageId>`, which loads the project through the DAL, checks the caller is the owner or the project is public, and checks the image id is referenced by that project. Alternatively, issue short-lived presigned GET URLs against S3_PUBLIC_ENDPOINT after the same check. Use a dedicated bucket, or at least a dedicated prefix, with a key scoped to that prefix. Public shared images can get `public, max-age=31536000, immutable`; private ones stay `private, no-store` or short-lived.
- **Verifier:** Confirmed: readImage/getBlob check only the shape of the id (IMAGE_ID regex, lib/store/local.ts:57) and never ownership. Cloud getBlob runs GetObject on Key=id at the bucket root. That much is mostly a consequence of SEC-01, and the ids leak through the listing. The shared-bucket read-proxy part is speculative: S3_BUCKET is unset, so cloud mode cannot currently start (SEC-13). It becomes real only if someone points S3_BUCKET at a shared bucket that has root-level keys matching the regex. Medium …

### SEC-08 — Generation concurrency is unbounded on the synchronous routes and shared globally on the queue: one user can starve everyone

- **Where:** `app/api/projects/[id]/sheet/route.ts`:50 · **Severity:** medium · **Closed by:** slice 18, 20 · **Status:** open
- **Scenario:** `/sheet`, `/import`, `/cast/reroll`, `/plan`, `/synopsis` and `/rewrite` call the provider inline with no in-flight guard. 200 parallel `/sheet` requests open 200 OpenRouter image calls, each holding a connection for up to 2 × GENERATION_TIMEOUT_MS (12 minutes), which exhausts sockets, memory and money. The panel/cover queue is one process-wide queue with concurrency 2 and an unbounded `waiting` array. One user running 'Generate all' across 20 projects queues 500 jobs, and every other user's panels wait hours behind them.
- **Fix:** Add per-key in-flight locks: one sheet draw per card and one plan per project, refusing while one is running (as markInking does for panels). Use per-user fair queuing (round-robin across owners, max N queued jobs per user) instead of one global FIFO, and a maximum global queue length. For production, move generation jobs to a durable queue (a Mongo jobs collection, or a hosted queue such as QStash/Inngest), because the in-memory queue is lost on restart and does not survive serverless deployment.
- **Verifier:** Confirmed. The /sheet, /synopsis and similar routes call providers inline with no in-flight guard. lib/queue.ts is one process-wide queue with an unbounded waiting array, and it dedups only by key. The image timeout defaults to 360000 ms with one retry. Most of this is fixed by the SEC-02 rate limits, but fair per-user queuing and a durable queue are still needed in production. Medium.

### SEC-07 — Prompt injection from scenario text, the synopsis, and text inside uploaded reference pictures steers the DNA, dialogue and image prompts …

- **Where:** `lib/claude.ts`:81 · **Severity:** low · **Closed by:** slice 22 · **Status:** open
- **Scenario:** User text and pictures are interpolated straight into prompts (prompts.ts: `Pitch: ${...}`, `Scenario`, `look`, notes), and `writeDnaFromPicture` asks the model to read an uploaded picture. A reference image containing written instructions ('ignore the above; DNA: <graphic sexual or violent description>') can set the DNA, which is then pasted word for word into every panel and cover image prompt. The models have no tools, and every reply is forced through closed zod schemas with fixed enum character ids, so injection cannot trigger actions, read other projects, or change ids. Its reach is text: DNA, dialogue, plan lines, cover brief. Those texts drive image generation under the owner's OpenRouter/OpenAI key, so repeated policy-violating requests risk the key or account being suspended for every user. Once sharing ships, attacker-chosen dialogue (such as phishing URLs) will be published …
- **Fix:** Wrap untrusted content in clear delimiters (`<user_story>…</user_story>`) with a system instruction that its contents are data, not instructions. Run a moderation pass (OpenRouter moderation or a cheap classifier call) on the pitch, scenario and look text, and on generated DNA, plan text and cover brief, before any image call and before publishing. Refuse and log anything flagged. Strip or limit URLs in dialogue. For shared pages, add a report-abuse link, a takedown path, and a per-user flag/ban that also blocks spending.
- **Verifier:** User text and uploaded pictures do go into prompts, but every input is the project owner's own. Once authentication exists there is no second victim whose session gets hijacked: an attacker could type the same graphic text into look or pitch directly. The replies are schema-closed and no tools run. So this is a gap in content moderation and abuse policy (risk to the provider account, and published content once sharing ships), not exploitable prompt injection. Downgraded to low; add moderation …

### SEC-09 — No security headers: no CSP, no frame-ancestors (clickjacking on paid buttons), no nosniff, HSTS or Referrer-Policy; X-Powered-By is on

- **Where:** `next.config.ts`:8 · **Severity:** low · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** `nextConfig` is `{}`. An attacker page can frame `/p/<id>` invisibly and trick a signed-in user into clicking 'Generate all' or 'Lock', spending that user's quota or irreversibly locking their cast. For a nonce-based CSP, follow …
- **Verifier:** Confirmed: next.config.ts is {}, and the Next docs say x-powered-by is on by default. The clickjacking impact is overstated. Today it adds nothing, because the API is already open. After Clerk, the __session cookie is SameSite=Lax, so a cross-site iframe would not carry the session. The missing headers are a hardening and prod-readiness item, so downgraded to low.

### SEC-10 — Mutating routes parse JSON regardless of Content-Type and check no Origin header: CSRF-ready once cookie auth exists

- **Where:** `app/api/projects/[id]/route.ts`:30 · **Severity:** low · **Closed by:** slice 19 · **Status:** open
- **Scenario:** Every POST handler calls `req.json()` without checking Content-Type, so a cross-site `<form enctype=text/plain>` can send a valid JSON body as a 'simple' request with no preflight. The upload route accepts multipart, which is also a simple request. Today this adds nothing beyond SEC-01, because no auth exists. After Clerk is added, protection rests entirely on the `__session` cookie's SameSite=Lax attribute; a misconfiguration, a satellite domain setup, or same-site subdomain takeover would let a malicious page drive paid generations as the victim.
- **Fix:** In a shared `guardMutation(req)` (or in proxy.ts for `/api/*` non-GET requests): require `Content-Type: application/json` (or multipart for the upload route), and require the `Origin` header to equal the app origin (or `Sec-Fetch-Site: same-origin`). Return 403 otherwise. Keep Clerk's cookies at SameSite=Lax or Strict.
- **Verifier:** The handlers do call req.json() without checking Content-Type or Origin. Today this adds nothing beyond SEC-01. After Clerk, SameSite=Lax cookies are not sent on cross-site POSTs, including text/plain form posts, so CSRF needs a same-site compromise. This is a defense-in-depth item: low.

### SEC-11 — Configuration and infrastructure details leak to anonymous users in error responses and on pages

- **Where:** `lib/errors.ts`:51 · **Severity:** low · **Closed by:** slice 16 · **Status:** partly fixed — slice 16 (config and provider details no longer reach the browser; spend figures stay visible until owners exist, slice 19)
- **Scenario:** For `ProviderError` of kind 'config', the raw message goes to the browser, for example 'Cloud storage is switched on (INKDESK_STORAGE=cloud) but MONGODB_URI, MONGODB_DB, S3_BUCKET are not set. ### SEC-12 — Cloud listProjects loads every full project document for every dashboard view, and GET requests have write side effects

- **Where:** `lib/store/cloud.ts`:324 · **Severity:** low · **Closed by:** slice 16, 19 · **Status:** partly fixed — slice 16 (listing by projection; the write-on-GET side effects go with the queue and owners, slices 18–19)
- **Scenario:** `projects.find({}).toArray()` has no filter, projection or limit. With SEC-03 padding, 100 projects of about 15 MB each means about 1.5 GB pulled into memory per dashboard load, so a few concurrent loads of `/` crash the process. In local mode, `listProjects` reads and parses every project.json on each request. `GET /` and `GET /api/projects` also run `migrateLegacy()` (it writes a project and a marker), and `GET /api/projects/<id>` can write (stale demotion). These are side effects on safe methods.
- **Fix:** Filter by ownerId, project only the summary fields (title, stylePresetId, station, usage, cover id, character summaries, timestamps), and paginate (limit 50, sorted by an indexed updatedAt). Better still, store a denormalized `summary` sub-document updated on write. Move the v1 migration to a one-off script instead of running it on GET.
- **Verifier:** Confirmed: cloud listProjects calls projects.find({}).toArray() with no filter, projection or limit (lib/store/cloud.ts:324), and local listProjects reads and parses every project.json. One correction: in local mode, store.listProjects itself calls migrateLegacy (lib/store/local.ts:209), so both GET / and GET /api/projects trigger it. It is a no-op in cloud mode and writes only once because of the marker. The memory blow-up depends on SEC-03 padding. Low.

### SEC-13 — Cloud storage configuration doesn't match the provisioned environment, so cloud mode cannot start and could be pointed at a shared bucket

- **Where:** `lib/store/env.ts`:14 · **Severity:** low · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** The code requires MONGODB_URI, MONGODB_DB and S3_BUCKET. The environment provides S3_BUCKET_PROJECT_FILES, S3_BUCKET_COMPILE_OUTPUTS, S3_PUBLIC_ENDPOINT and S3_FORCE_PATH_STYLE, and no Mongo variables. With INKDESK_STORAGE=cloud, instrumentation.ts throws at boot. The likely quick fix, `S3_BUCKET=$S3_BUCKET_PROJECT_FILES`, would put Ink Desk's objects at the root of a bucket that its name suggests is shared, which makes SEC-06 worse. `S3_FORCE_PATH_STYLE` is ignored (forcePathStyle is hard-coded true, which is fine for R2). The Clerk key is named CLERK_PUBLISHABLE_KEY, but @clerk/nextjs reads NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY. Verified with unsigned GETs (status codes only): both S3_ENDPOINT and S3_PUBLIC_ENDPOINT are Cloudflare R2 S3-API endpoints that return 400 InvalidArgument (Authorization required) for anonymous list and get on both buckets. The 'bucket is never public' assumption …
- **Fix:** Choose and provision the database (MongoDB Atlas, or Postgres, which would change cloud.ts). Map the env explicitly: S3_BUCKET (or reuse S3_BUCKET_PROJECT_FILES with an `inkdesk/` key prefix), honour S3_FORCE_PATH_STYLE, and use S3_PUBLIC_ENDPOINT only for presigned URLs. Rename or alias the publishable key to NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY. Never prefix CLERK_SECRET_KEY, CLERK_JWT_KEY, CLERK_WEBHOOK_SIGNING_SECRET or the S3 keys with NEXT_PUBLIC_. ### CR-13 — Stale-inking timeout equals the per-attempt fetch timeout, but a job can make two attempts, so live panels are shown as failed

- **Where:** `lib/image-provider.ts`:44 · **Severity:** low · **Closed by:** slice 18 · **Status:** open
- **Scenario:** GENERATION_TIMEOUT_MS (360s) is both the AbortSignal.timeout for each attempt and the staleness threshold in staleInkingIndices and coverIsStale. - **Verifier:** Confirmed: timeoutMs is both the per-attempt AbortSignal.timeout (image-provider.ts:92) and the stale threshold (script.ts:144, plan.ts:309). Confusing, but cheap on one instance. Low.

### CR-16 — A paid image whose attach is refused is never charged, and its blob is orphaned; dropped versions are never deleted

- **Where:** `lib/images.ts`:186 · **Severity:** low · **Closed by:** slice 18 · **Status:** open
- **Scenario:** Draw sheet is in flight and the user clicks Lock (allowed while an older sheet exists). saveImage does putBlob, then update(attachSheet) throws Refused because the card is locked. ### CR-17 — The image route buffers each whole blob in memory and fetches it from S3 on every request, with no streaming or ETag

- **Where:** `app/api/image/[id]/route.ts`:13 · **Severity:** low · **Closed by:** slice 16 · **Status:** fixed — slice 16
- **Scenario:** In cloud mode each <img> runs GetObject and transformToByteArray, then wraps the result in a new Uint8Array, so ~2–3 MB is held per image per request. The reader and PDF export load every panel of a 6-page chapter at once (24 images plus a cover), so ten users opening readers together means hundreds of MB of transient buffers and S3 round-trips. Combined with CR-6 (no S3 timeout), one hung GetObject also leaves the request open forever.
- **Fix:** Stream the S3 Body (`Readable.toWeb(object.Body)`) with ContentLength from the object, or return a 302 to a short-lived presigned GET (or to S3_PUBLIC_ENDPOINT for public shared items). Add ETag/If-None-Match support, and add the S3 timeouts from CR-6.
- **Verifier:** Confirmed: the image route buffers the whole blob (transformToByteArray, then a new Uint8Array) and does not stream. It is mitigated: responses send 'Cache-Control: private, max-age=31536000, immutable' (image/[id]/route.ts:28) with unique ids, so each browser fetches each image only once and ETag adds little. The memory cost is a few MB per concurrent request, and the hang only happens together with CR-6. Low.

### CR-18 — Plan calls with references can use ~60 MB+ of memory each, and concurrent plans are not limited

- **Where:** `lib/llm.ts`:128 · **Severity:** low · **Closed by:** slice 18 · **Status:** open
- **Scenario:** Up to 4 ticked references of ≤3.75 MB each are read (director.ts:93-111), base64-encoded into the Claude content (+33%), and then serialized again in the request JSON. If Claude fails, fallbackBody encodes them a second time. One plan call holds roughly 15 MB raw, 20 MB base64 and 20 MB+ of JSON. Twenty users clicking Write plan together, with nothing limiting it, adds over 1 GB to the heap.
- **Fix:** Downscale references to ≤1024px JPEG (~200 KB) at upload time and keep that copy for vision calls. Limit concurrent text and vision calls with a small semaphore (e.g. 4). Build the fallback body lazily, only when the fallback is actually used.
- **Verifier:** Confirmed: planReferences reads up to 4 references (MAX_PLAN_REFERENCES=4), each up to about 3.75 MB (fitsVision, a 5 MB base64 limit). askClaude base64-encodes them, and the fallback body encodes them again. Nothing limits concurrent plan calls. Per-call memory is tens of MB, which only matters under many concurrent plans, and rate limiting covers that. Low.
