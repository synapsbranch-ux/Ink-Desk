Ink Desk

An AI manga creator studio: you pitch a story idea, and the app turns it into a real manga page with your own characters drawn consistently across every panel.

v3 · Draft — awaiting review v1 · v2 approved Proof of concept 2–4 hours active Canonical: scope.md

New, 2026-10-14: a draft revision — Ink Desk Studio v3, public on the learner’s domain — is at the end of this page, with its Changes Since Approval. v1 and v2 stay above, unchanged, as the record of what was built.

The unique kernel

Locked appearance, free action

Locked

The app can change what a character does in a panel — never what they look like.

Each character gets a model sheet generated once, then frozen. Locking freezes two things, and both travel with every single panel request:

1 · Visual reference
The sheet image itself, sent to the image model — “so the face, hair and outfit come from a picture and not just from words.”
2 · Visual DNA
Text Claude writes once at character creation — hair, eyes, face shape, outfit, colors, one or two distinguishing marks. Pasted word for word into every panel prompt, never rewritten.

Why this is the kernel: most AI comic tools change the hero’s face in every panel. Delete this and Ink Desk is a generic prompt-to-image toy.

The core loop

Five stations, start to page

Station 1 · Story — the pitch desk

One prompt box, plus genre and tone selection. Claude returns a synopsis you accept or rewrite — “editable, never final.”

Station 2 · Cast — model sheets

This is where the kernel is built. Two characters. Each gets DNA text from Claude and one single image laid out as a real model sheet — front, three-quarter and a few expressions in one frame. That one image is the canonical reference. No cropping it into separate frames.

You do
Describe each character in a line. Then hit lock.
Claude Sonnet writes
The visual DNA text.
GPT Image draws
One sheet image per character — 2 generations.
Locks
Sheet image + DNA text. Unlocking and editing a sheet is out of scope.

Station 3 · Page script — the breakdown

Once the synopsis is accepted, Claude writes the script for all four panels. This step is load-bearing: the script is the variable half of every panel prompt.

Claude Sonnet writes
Per panel: which character, the action, the camera angle, the background, and the dialogue.
Hard constraint
Exactly one locked character per panel, so each request carries a single reference.
Feeds
The dashed box in the diagram above.

Station 4 · Storyboard — the main studio

Four panels generated against the locks, each prompt carrying only that panel’s character sheet and DNA. Panels generate in the background with visible per-panel progress.

GPT Image draws
4 panels — one generation each, never two.
You do
Check each face against the sheet. Redraw panel if it misses.
Redraw means
Same request, same references. Keeps the previous version so you can switch back. Never touches other panels.
No manual painting
If a redraw is still off, you accept the best one.

Station 5 · Ink & Publish — the reader

Full-page reading. The pencil-to-ink reveal plays once the page is ready.

The ink-in effect
Theatrical, not real. A reveal animation over the finished image — same look on camera, half the generations.
Lettering
Bubbles overlaid in Comic Neue, never drawn by the image model.
Controls
Right-to-left toggle (kept — it’s a CSS flip and very manga for the cost).
Export
PNG, compositing image and bubbles together.

What “working” looks like

The money shot

Success criterion

Each character is recognizably themselves in every panel they appear in.

Stated per-character on purpose: shot/reverse-shot means no one appears in all four panels. Kaito is in 1 and 3, Mio in 2 and 4. The claim is continuity across their panels — not one face across the whole page.

The boundary

Now, later, cut

Nothing disappears silently. Open each to see what’s inside and why.

Now In the proof of concept 5 stations
  • Story — pitch box, genre and tone, editable Claude synopsis.
  • Cast — two characters, each with DNA text and one single sheet image, locked.
  • Page script — Claude’s 4-panel breakdown, one locked character per panel.
  • Storyboard — 4 panels generated against the locks, per-panel Redraw with version switching, dialogue overlaid as bubbles in Comic Neue.
  • Ink & Publish — full-page read, pencil-to-ink reveal, right-to-left toggle, PNG export compositing image and bubbles.

Three deliberate risk cuts

  • The ink-in effect is theatrical. One generation per panel; the transition is a reveal animation. Same look on camera, no second consistency risk.
  • One reference image per request. Single-character panels mean the app never sends two sheets at once.
  • No text in generated images. Lettering is app-side overlay, so the image model is never asked to render type.

Budget: roughly 2 sheets + 4 panels = 6 images per full run, plus redraws.

Later Worth doing, just not now 9 items
  • A panel with both characters together — needs multi-reference generation. The main reason it’s deferred.
  • Director’s Chair chat for directing Claude on a selected panel.
  • Script Strip for editing dialogue line by line.
  • Backgrounds and scenes shelf as separately generated, reusable assets. For now, background folds into the panel prompt.
  • Multiple page layouts — the mockup has three (5-panel, 3-panel splash, 4-panel with an SFX insert).
  • PDF export; share link.
  • Unlocking and editing a sheet after it’s locked.
  • External comic APIs such as LlamaGen.
  • Deployment — optional for this hackathon.
Cut Named, with reasons 5 items
  • Real two-pass pencil→ink generation Doubles image cost and adds a second chance for the face to drift, for an effect on screen for ~1.4 seconds. A CSS reveal is indistinguishable on camera.
  • Five-frame model sheets Separate front / three-quarter / expression images cost five times as much, drift five ways, and leave no single canonical reference to send. One sheet image solves all three.
  • Manual panel touch-up or painting The only repair is Redraw. Keeps the loop honest and the build small.
  • A third character The mockup’s Old Tetsu. Two characters prove the lock isn’t a fluke; a third adds cost without adding proof.
  • Reusing the mockup’s code It’s a design reference, and it fakes all art with CSS. The styling language carries over; the implementation does not.

Carried forward

Open questions, by owner

Verify in 4-spec

  • Which GPT Image model and endpoint accept reference images, and how many per request. The whole kernel rests on this. Verify before building Cast — it’s the one assumption that could force a redesign.
  • Image cost and rate limits at ~6 images per run plus redraws.

Resolve in 3-prd

  • What the user sees while panels generate — per-panel progress, partial page reveal.
  • Hard failure handling — not “the face is wrong,” but 429s, timeouts, refusals, malformed responses.

Latency direction already set: panels generate in the background with visible per-panel progress; the reveal plays once the page is ready. The demo video may trim the waiting, but the generation itself has to be real — no pre-baked images.

Revision · 2026-10-13 · decided by the learner

Ink Desk Studio (v2) — from one page to a chapter

After the v1 final review the learner's verdict was: "not really an AI manga creator with chapters and volumes — much more a single storyboard creator." v1 is complete and tagged v1-poc; it stays the fallback submission. v2 is the smallest studio that makes a three-minute video prove manga creator, with a feature freeze on 2026-10-20 and a cut line written in advance.

The kernel, restated: one contract on three things

Locked appearance, free action — for the character, the style, and the setting.

The app can change what happens in a panel, never how the character, the art style or a locked place looks. The character lock is the anchor and the only one proven. Style and setting are candidate locks until each passes its own kernel test (one reference image, three panels at medium); until then the video does not claim them. An imported reference is just another way to create a lock: the learner's image replaces the generated sheet, same contract.

The v2 loop

What "working" looks like now

One character, one chapter, several pages. The imported character's reference image beside panels from page 1, page 2 and page 3 plus the cover — close-up, medium, wide — same face, same outfit, same marks. Success: each locked character is recognizably themselves in every panel they appear in, across every page and on the cover; an imported character recognizably matches the upload. A second style as a short showcase is optional and not a criterion.

Providers (v2) — verified 2026-10-13

  • Text: Anthropic claude-sonnet-5-5 first; fallback openai/gpt-5.6-terra through OpenRouter chat completions with strict JSON schema, the same zod schemas validating the reply.
  • Images: OpenRouter openai/gpt-image-2.5-sunburst (proven); other models are candidates behind a kernel test.

The learner’s word: “base on the devpost skill and also what the hackathon says i want you to remove clerk auth to betterauth … be careful to not leave stuff not implemented” (and “no there is no clerk account”: nothing to migrate). The same day the learner cut Google and GitHub sign-in: “make sure only email and password sign in / up are there and no google and github” — sign-in and sign-up are email and password only.

The kernel, extended to motion

Candidate

Locked appearance, free action — and now free motion.

The character lock stays the anchor and the only proven claim. v3 extends the same contract to motion: an animated shot starts from a panel that was drawn from the locked sheet, carries the locked appearance, and is free only in movement and camera.

The motion clause is a candidate lock until its own kernel test passes: the imported character animated across at least three shots (close-up, medium, wide), still the same face, outfit and marks from the first frame to the last frame of each shot. That is the money shot of the v3 demo video.

Verified 2026-10-14, and it changes the learner’s first idea: one Seedance request cannot carry both a first frame and reference images — first/last-frame mode and reference mode are exclusive (OpenRouter’s video docs and ByteDance’s own). So the motion kernel test compares the two allowed ways:

Mode A · first frame
The panel as the first frame; the face is carried by the panel alone.
Mode B · references
The panel and the locked sheet both as references, with the prompt naming the panel as the opening frame.
Who decides
Which one becomes the method is the learner’s decision after seeing the test. See spec.md > Revision v3 > Verified for v3.

The v3 loop

The v2 studio sits in the middle, unchanged. What v3 adds wraps around it: an account in front, a page animation and a public link behind.

What “working” looks like (v3)

“I open a finished chapter in the dashboard, click ‘Animate’, see the cost estimate and confirm. Each shot shows its own progress, and the other shots continue if one fails.”

What comes back

A 20–30 s trailer of one page — one Seedance shot per panel (3–5 s each, bytedance/seedance-2.0 through OpenRouter), camera motion written from the panel’s stored camera field, bubbles revealed on time, one ElevenLabs voice per character speaking the dialogue, music, assembled with ffmpeg in the worker. It lives in the dashboard, is stored in the bucket, and is shareable through a public link on the domain.

And the public app

A stranger can sign up with an email and a password make a small chapter inside a free quota, and cannot see, change or spend anyone else’s work; when a limit is reached the buttons say why and when it resets; the whole thing works on a phone.

Now, later, cut — v3

Feature freeze 2026-10-22, end of day. The “Now” list is in the order the learner set — risk first.

Now In the submission 10 items
  • 1 · Domain and hosting. Railway, two services from main: the Next.js web app and a separate worker. Custom domain with HTTPS; the domain root goes straight into the app (signed-out → sign-in, signed-in → dashboard) — no landing page. One source of truth for the URL (APP_URL, NEXT_PUBLIC_APP_URL). A health check Railway deploys against, and a calm status message when the worker or Redis is down.
  • 2 · Storage. MongoDB is the source of truth for projects, users, jobs, videos, shares and reports; the bucket holds every image, video and audio file, private, served only through routes that check the owner first (as built, 2026-10-24: no signed URLs); public access only through share links. The local adapter stays for development. The generated art and media that git should not carry move to the bucket.
  • 3 · Queue. Redis + BullMQ on Railway: image and video queues (and, as built, an account queue for export and deletion; a trailer’s speech and music run inside its video job) with retries, back-off, timeouts, stalled-job recovery and per-queue concurrency (2 for images, 1 for video). Mongo keeps job status and results, so progress and history survive a Redis flush.
  • 4 · Auth and ownership. Better Auth (open source, inside the app, accounts in the studio’s own MongoDB) with email and password only (Google and GitHub cut at the learner’s word, 2026-10-24); every route requires sign-in except sign-in/sign-up, the public share pages, Terms and Privacy, and the health check. Each account is mirrored into the studio’s own user record as it is made. Every resource is checked against the signed-in user on the server (no IDOR). No CAPTCHA and no email service: sign-in and sign-up are rate-limited per address instead, and a password account’s email stays unverified (so it never matches the allowlist or the admin list; the learner’s judge:account script is the one way an address is marked verified). (Clerk until 2026-10-24 — see Changes Since Approval, item 9.)
  • 5 · Limits. Per-user and per-IP rate limits on sign-up, generation and upload routes; daily per-user quotas (a new account gets a small free quota, e.g. 1 project, 20 images, 1 short video a day; higher limits only for allowlisted emails — the learner, testers, a judge demo account); a global daily spend kill switch, starting at $5/day for all users, that pauses generation with a clear message. The same counters drive the header meter, the Usage page and the enforcement.
  • 6 · Studio features. The dashboard as home (projects, manga, videos, library, quota meter, New project); Settings (the account — email, how it signs in, change password, signed-in devices — studio defaults, my shared links with unpublish, export my data, delete my account and everything with it); Usage (today vs limit for images, video seconds, audio characters, reset time, spend today and this month from real usage.cost, the plan, an 80% warning); public sharing of manga and videos on /s/<token> with Open Graph previews, noindex, and a Report button whose reports reach the learner; Terms and Privacy pages linked from sign-in and Settings.
  • 7 · Video generation. The one-page trailer above, behind its estimate and the caps.
  • 8 · Responsive and polish. Every screen works on mobile, tablet and desktop, following the 5b rules (visible actions, explained disabled states, real loading states).
  • 9 · Production readiness and security. Environment validated at boot, HTTPS only, security headers and a CSP that allows only the studio’s own origin (no outside script, frame or image host), structured logs with no secrets or personal data, error tracking, graceful failures, and a security and stability audit before and after the build, written to devpost/security-report.md with severity and fix status.
  • 10 · The judge demo account with a pre-made chapter and video; its credentials go in the Devpost testing instructions, which the learner writes.

The v2 studio scope stays as agreed: projects with a locked style, the library with imported references, the Director’s chapter plan, the multi-page reader, PDF export, the text fallback to openai/gpt-5.6-terra.
